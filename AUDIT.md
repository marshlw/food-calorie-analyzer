## 1. Как устроена система сейчас

### 1.1. Модель исполнения запросов

**Эндпоинты, которые ходят в БД или на диск, объявлены обычными `def`, а не
`async def`.** FastAPI выполняет их в threadpool anyio (лимит зафиксирован на
40 потоков в startup-хуке). Это не стилистика: SQLAlchemy здесь синхронный
(psycopg2), и в `async def` каждый запрос к БД блокировал бы event loop —
воркер переставал бы обслуживать всё остальное на время запроса.

`async def` остался ровно там, где есть настоящий `await`:

| Эндпоинт | Почему async |
|---|---|
| `/health`, `/me` | нет I/O вообще |
| `/uploads/{filename}` | только stat файла, отдача через `FileResponse` |
| `/advisor`, `/advisor/ask` | `run_in_threadpool` для БД + отдельный пул под LLM |

Правило зафиксировано комментарием в `main.py` перед секцией эндпоинтов.
Добавляя эндпоинт с обращением к БД, объявляйте его `def`.

### 1.2. Соединения с БД

Зависимость `get_db` **одна** — из `app/database.py`. Её используют и
`auth.get_current_user`, и все эндпоинты, поэтому FastAPI кэширует её в
рамках запроса и берёт **одно** соединение на HTTP-запрос. Раньше в
`main.py` был собственный дубликат `get_db`, из-за которого каждый запрос
занимал два коннекта и делал лишний `SELECT users`.

Бюджет коннектов при `max_connections=150`:

```
api    2 процесса uvicorn × (POOL_SIZE 5 + MAX_OVERFLOW 5) = 20
celery 1 процесс (пул потоков)                             = 10 на 8 задач
beat   1 процесс                                           ≈ 1
```

`pool_timeout=10` — под пиком запрос лучше упадёт быстро, чем будет 30 секунд
держать поток ради клиента, который уже отвалился по своему таймауту.

Под 5000 DAU следующий шаг — PgBouncer в режиме `transaction`.

### 1.3. Схема БД и деплой

Схемой владеет **Alembic**. Сервис `migrate` в `docker-compose.prod.yml`
выполняет один раз:

```
alembic upgrade head && python -m app.bootstrap
```

`api` и `celery` ждут его через `condition: service_completed_successfully` —
если миграция упала, приложение не поднимется. Это намеренно.

- `alembic upgrade head` — схема. Миграция `0004_schema_baseline` идемпотентна
  и рассчитана на два сценария: чистая БД (создаёт всё) и существующая
  прод-база, никогда не помеченная alembic (доливает недостающее).
- `python -m app.bootstrap` — данные: засев справочников продуктов и
  упражнений, backfill разделения белка. Тоже идемпотентно.

**Startup-хук приложения не трогает БД вообще.** Раньше там были `create_all`,
`ALTER TABLE ADD COLUMN`, `CREATE INDEX`, seed и backfill — и всё это на
старте *каждого* воркера: гонка на DDL между воркерами, `ACCESS EXCLUSIVE`
lock на живой таблице, полное сканирование `meal_entries` при каждом деплое.

`database.ensure_schema()` сохранён, но помечен как **dev/test only**.
Вызывать его из startup нельзя.

### 1.4. Аутентификация

- **Пароли** — bcrypt с обрезкой до 72 байт, `gensalt()`.
- **Access-токен** — 30 минут, claim `tv` (token version).
- **Refresh-токен** — 7 дней, **одноразовый**. При обмене его `jti` гасится в
  Redis; в ответ приходит новая пара.
- **Детекция повторного использования.** Предъявление уже погашенного `jti`
  трактуется как компрометация: инкремент `users.token_version` мгновенно
  обнуляет все токены пользователя, включая те, что успел получить
  злоумышленник.

Две защиты от ложных срабатываний — без них система разлогинивала бы людей
на ровном месте:

1. **Grace-окно 20 секунд.** Две вкладки читают один refresh из localStorage
   и обновляются почти одновременно. Внутри вкладки гонку снимает
   `tokenRefreshPromise` в `frontend/src/api/axios.ts`, между вкладками —
   только это окно.
2. **Сторож `refresh_store:alive`.** Если `jti` не найден *и* сторожа нет,
   значит Redis потерял данные (переезд, FLUSHALL, потеря AOF), а не кто-то
   предъявил краденый токен. Пропускаем.

Если Redis недоступен, ротация деградирует до прежнего поведения (токен живёт
до `exp`) — падение Redis не должно разлогинивать всех.

Токены без `jti` (выданные до внедрения ротации) проходят один раз, поэтому
раскатка не разлогинивает пользователей.

### 1.5. Анализ фото

**Ошибки анализа не глотаются.** `ml_service.analyze_image_sync` поднимает:

| Исключение | Когда | Поведение задачи |
|---|---|---|
| `AnalysisError` | все провайдеры отказали, таймаут, сеть | ретрай 3 раза (30/60/120 с), затем FAILURE |
| `AnalysisPermanentError` | файла нет, файл битый | сразу FAILURE, без ретраев |

При окончательной неудаче **попытка возвращается в дневной лимит** —
списывать её за анализ, которого не было, нечестно.

Раньше при отказе всех провайдеров возвращался `DEFAULT_FALLBACK`
(`food: "unknown"`, 200 ккал), задача помечалась SUCCESS, `autoretry_for`
никогда не срабатывал, а пользователь получал выдуманные цифры, заплатив
попыткой из лимита.

Ретраи делаются вручную через `self.retry`, а не через
`autoretry_for=(Exception,)`: с ним нельзя различить временный сбой и
постоянную ошибку.

### 1.6. Очереди Celery

Три очереди, чтобы редкая тяжёлая задача не занимала слоты, где пользователи
ждут результат анализа:

| Очередь | Задача | Кто слушает |
|---|---|---|
| `analyze` | `analyze_image_task` | `celery_worker` |
| `maintenance` | `cleanup_uploads_task` | `celery_worker` |
| `retrain` | `retrain_model_task` | **никто** (ретрейн выключен) |

**Воркер работает на пуле потоков** (`--pool=threads --concurrency=8`), не на
префорке. Задача на 95% состоит из ожидания ответа Yandex Vision (20–45 с),
CPU почти не нужен. Префорк с concurrency=6 — это 6 полных процессов Python
с Pillow, ~120 МБ каждый ещё до первой картинки: на ВМ с 2 ГБ RAM это не
помещается рядом с Postgres и api. Бонус: 8 потоков берут 8 коннектов из
одного пула, а 6 префорк-процессов держали бы 6 отдельных пулов.

**Чем платим:** пул потоков не применяет `task_time_limit` /
`soft_time_limit` и `--max-tasks-per-child` — celery умеет прерывать задачи
только в префорке. Насмерть зависнуть задача не может: у httpx-клиента
жёсткий `MODEL_TIMEOUT_SECONDS`, размер картинки ограничен
`MAX_IMAGE_PIXELS`, утечки ловит `mem_limit: 700m` + `restart`.

Значения лимитов в `celery_app.conf` оставлены для префорк-запусков (dev,
отдельный воркер ретрейна).

### 1.7. Диск

`cleanup_uploads_task` запускается по расписанию celery-beat в 03:20 UTC и
удаляет файл, если он **старше `UPLOAD_RETENTION_DAYS` (30) ЛИБО осиротел** —
на него не ссылается ни `tasks.image_path`, ни `meal_entries.photo_path`, ни
`feedback.image_path`. Сюда же попадают промежуточные `p_*.jpg`, которые
оставляет `ml_service.preprocess`.

Файлы младше суток не трогаются **никогда**, даже если выглядят
осиротевшими: между сохранением файла и коммитом строки в БД есть окно.

Если прочитать ссылки из БД не удалось, уборка прерывается целиком — лучше не
удалить ничего, чем удалить нужное.

Записи в БД не меняются: у приёма пищи остаются КБЖУ, пропадает только
картинка. `photo_url` продолжает отдавать подписанную ссылку, она вернёт 404,
и `<img>` в `MealDetail.tsx` обрабатывает `onError`, показывая плашку
«нет фото».

Свободное место логируется после каждой уборки; ниже
`UPLOAD_DISK_FREE_ALERT_GB` (5 ГБ) — уровень ERROR.

Оценка роста: 5000 DAU × 1,5 фото × ~400 КБ ≈ 3 ГБ/сутки, то есть 30 дней
≈ 90 ГБ. Уменьшайте retention, если диск меньше.

### 1.8. Загрузка изображений

Цепочка проверок в `_save_upload_file_securely`:

1. allowlist расширений;
2. запись во временный файл с контролем `MAX_UPLOAD_SIZE` (10 МБ);
3. **проверка разрешения до декодирования** — `Image.open()` читает только
   заголовок, поэтому `.size` известен без разворачивания пикселей. Выше
   `MAX_IMAGE_PIXELS` (30 Мп) — отказ. Один только `verify()` от
   decompression bomb не защищает: он тоже не декодирует пиксели, а
   10-мегабайтный PNG разворачивался бы в сотни МБ RSS уже в воркере;
4. `verify()` + проверка формата;
5. нормализация в JPEG (EXIF-поворот, удаление метаданных);
6. переименование в UUID и атомарный `os.replace`.

В `ml_service` дополнительно выставлен жёсткий `Image.MAX_IMAGE_PIXELS` на
весь процесс воркера — страховка для фото, пришедших другим путём.

Бюджет памяти: 30 Мп × 3 байта = ~90 МБ + копия при `convert("RGB")` ≈ 180 МБ
на фото.

### 1.9. Лимиты

| Что | Лимит | Ключ |
|---|---|---|
| AI-анализ фото | `AI_DAILY_LIMIT` (5)/сутки | по пользователю |
| Советы `/advisor` | `ADVISOR_DAILY_LIMIT` (20)/сутки | по пользователю, **только при промахе кэша** |
| Вопросы `/advisor/ask` | 30/сутки | по пользователю |
| Сканирование штрих-кодов | 100/сутки | по пользователю |
| Попытки входа | `AUTH_RATE_LIMIT_ATTEMPTS` | по IP + по паре (email, IP) |
| Регистрации | `REGISTER_RATE_LIMIT_ATTEMPTS` | по IP |
| Админ-эндпоинты | 20/час | по IP |

Лимит советчика списывается через хук `before_llm` в `advisor.get_advice_async`
— только перед реальным обращением к модели. Вешать `enforce` на эндпоинт
было бы неправильно: пользователь сжигал бы попытки, просто открывая вкладку
с готовым советом.

**Ключ кэша советчика огрублён**: калории до 100, макросы до 25 г, вода до
250 мл. Раньше в хэш шёл весь контекст с точными значениями, и каждый стакан
воды инвалидировал кэш — следующее открытие вкладки давало новый платный
вызов на 40 секунд.

`_run_llm_with_timeout` ограничивает ожидание (`ADVISOR_LLM_TIMEOUT + 20`).
Оговорка: отмена не убивает уже запущенный поток, она освобождает только
HTTP-запрос.

### 1.10. Сеть и заголовки

**Доверие к X-Forwarded-For.** uvicorn запускается с
`--forwarded-allow-ips '172.29.0.10'` — это статический IP caddy в сети `web`
(подсеть зафиксирована в `networks`). uvicorn 0.27 сравнивает адреса строкой
и CIDR не поддерживает, поэтому именно IP, а не подсеть.

С прежним `'*'` uvicorn переписывал `request.client.host` любым присланным
заголовком ещё до нашего кода — вся brute-force защита обходилась
подстановкой случайного `X-Forwarded-For`.

Caddy заголовок **перезаписывает**, а не дополняет:
`header_up X-Forwarded-For {remote_host}`.

**CSP** задаётся в `Caddyfile`. Inline-скриптов на фронте нет — тема вынесена
в `/theme.js` именно ради `script-src 'self'`. `style-src` содержит
`'unsafe-inline'` (Tailwind/React ставят inline-стили) и Google Fonts,
`img-src` — `blob:` для предпросмотра и хосты Open Food Facts.

`/metrics` наружу закрыт: Caddy отвечает 404, изнутри сети backend метрики
доступны на `http://api:8000/metrics`.

### 1.11. Секреты

- Приложение **не стартует** с placeholder `SECRET_KEY` или словарным
  паролем БД (`config.model_post_init`).
- `POSTGRES_PASSWORD`, `APP_DB_PASSWORD`, `REDIS_PASSWORD` обязательны в
  `.env` — compose падает с понятной ошибкой, если их нет.
- `CELERY_BROKER_URL` и `CELERY_RESULT_BACKEND` **подставляются из
  `REDIS_URL`**, если не заданы явно. Пароль Redis задаётся ровно в одном
  месте, и нельзя получить конфигурацию, где API ходит с паролем, а Celery
  молча падает с NOAUTH.
- Строки подключения в логи не пишутся — только host:port.

### 1.12. Что проверено и претензий нет

- **SQL-инъекции** — весь доступ через ORM с параметризацией; `escape_like`
  корректно экранирует `%`, `_`, `\` перед `ilike`; `init.sh` использует
  psql-переменную `:'app_pw'` с автоквотированием.
- **Path traversal в `/uploads/{filename}`** — двойная защита:
  `filename != Path(filename).name` + проверка HMAC-подписи.
- **Аутентификация покрывает все эндпоинты**, кроме намеренно публичных
  (`/health`, `/register`, `/login`, `/token`, `/uploads` с подписью,
  `admin/*` с `X-Admin-Token`).
- **Проверка владения объектом** — задачи, приёмы пищи, фото, замеры,
  тренировки фильтруются по `user_id`. Последняя дыра (`task_id` из тела
  запроса в `POST /meals`) закрыта.
- **Фото не раздаются публичной статикой** — только по подписанным ссылкам
  с TTL.
- **Пагинация клэмпится** — `?limit=1000000` не выгрузит таблицу.
- **Целостность расчётов** — суммы КБЖУ составных блюд считаются на бэкенде,
  фронтовым суммам не доверяют.
- **N+1 в дневнике** решён через `selectinload`.
- **Circuit breaker** на ML-провайдерах и отдельный пул под LLM-советчика.
- **`/docs` выключается в проде** через `ENABLE_DOCS`.
- **Индексы автодополнения** — GIN + `pg_trgm` по `products.name` и
  `exercises.name`. Индекс строится по самой колонке, без `lower()`: запросы
  идут через `ILIKE`, а `gin_trgm_ops` по колонке обслуживает и `LIKE`, и
  `ILIKE`. Индекс по `lower(column)` планировщик для `ILIKE` не подхватит.

## 2. Эксплуатация

### 2.1. Порядок запуска

```
docker compose -f docker-compose.prod.yml up -d --build
```

Последовательность: `postgres` + `redis` (healthy) → `migrate` (отрабатывает
и завершается) → `api` (healthy) → `celery_worker`, `celery_beat`, `caddy`.

Если `migrate` упал — смотрите `docker compose logs migrate`. Приложение
намеренно не поднимется.

### 2.2. Обязательные переменные `.env`

```
POSTGRES_PASSWORD=...      # суперпользователь postgres
APP_DB_PASSWORD=...        # прикладной fooduser
DATABASE_URL=postgresql+psycopg2://fooduser:APP_DB_PASSWORD@postgres:5432/fooddb
REDIS_PASSWORD=...         # пароль Redis
REDIS_URL=redis://:REDIS_PASSWORD@redis:6379/0
SECRET_KEY=...             # подпись JWT
DOMAIN=...                 # для Caddy и Let's Encrypt
```

Генерация: `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`.
Пароль Redis не должен содержать `@`, `:`, `/` — они ломают разбор URL.

### 2.3. Проверки после деплоя

```bash
docker compose -f docker-compose.prod.yml logs migrate       # миграции прошли
docker compose -f docker-compose.prod.yml logs celery_beat   # расписание поднялось
docker compose -f docker-compose.prod.yml exec postgres \
  psql -U postgres fooddb -c "\di *trgm*"                    # индексы на месте
curl -s http://localhost:8000/metrics | head                 # метрики отдаются
```

В консоли браузера не должно быть нарушений CSP.

### 2.4. Флаги, о которых стоит помнить

| Настройка | Значение | Смысл |
|---|---|---|
| `RETRAIN_ENABLED` | `false` | в прод-образе нет ollama; включать только вместе с ним |
| `DELETE_UPLOAD_AFTER_ANALYSIS` | `false` | фото нужно на экране результата и для фидбека |
| `METRICS_ENABLED` | `true` | `/metrics`, закрыт снаружи через Caddy |
| `UPLOAD_RETENTION_DAYS` | `30` | срок жизни фото на диске |
| `MAX_IMAGE_PIXELS` | `30_000_000` | потолок памяти воркера |

## 3. Известные компромиссы

Решения, принятые осознанно. Если будете их менять — знайте, почему они
такие.

1. **Пул потоков у Celery вместо префорка** — экономия памяти в обмен на
   отсутствие `task_time_limit`. Обосновано тем, что все блокирующие вызовы
   имеют собственные таймауты. При переезде на ВМ с большей RAM префорк
   предпочтительнее.
2. **`0004_schema_baseline` использует живые `Base.metadata`**, а не
   замороженный снимок схемы. Проект вырос на `create_all`, и повторять всю
   схему руками означало бы завести второй источник правды. **Все
   последующие миграции должны быть обычными, с явными `op.add_column()`.**
3. **Ротация refresh деградирует при падении Redis** — доступность выбрана
   в ущерб строгости. Иначе недоступность Redis выкидывала бы всех
   пользователей.
4. **Grace-окно 20 секунд** ослабляет детекцию кражи в этом интервале. Это
   плата за корректную работу нескольких вкладок.
5. **In-memory fallback rate-limit** при недоступности Redis делает лимиты
   пер-процессными: при 2 воркерах реальный лимит удваивается. Приемлемая
   деградация, но она должна быть видна в мониторинге (см. M-12).
6. **Postgres опубликован на `127.0.0.1:5433`** вопреки утверждению в шапке
   compose. Только loopback, но комментарий врёт — см. M-4.

|---|---|---|---|
| M-2 | `literal(norm).like('%'\|\|Product.name\|\|'%')` | `ml_service.py` | Индекс невозможен в принципе — full scan `products` на каждый ингредиент каждого анализа (до 6 раз). Фикс: загрузить справочник в память процесса один раз, он мал и почти не меняется. |
| M-4 | Postgres опубликован наружу вопреки комментарию | `docker-compose.prod.yml` | Шапка утверждает «ни одного `ports:`», но порт `127.0.0.1:5433:5432` есть. Не критично (только loopback), но при следующей правке легко превратится в `0.0.0.0`. |
| M-6 | Контейнер работает от root | `Dockerfile` | Нет `USER`. `no-new-privileges` есть, но это не то же самое. Требует `chown` существующего тома `uploads_data` на ВМ, иначе запись фото сломается. |
| M-9 | CORS с localhost и `allow_credentials=True` в проде | `config.py`, `main.py` | Восемь localhost-origin'ов зашиты в дефолт и не убираются в проде. `expose_headers=["*"]` вместе с credentials — невалидная по спецификации комбинация. |
| M-12 | In-memory fallback rate-limit логируется как `warning` | `rate_limit.py` | Должно быть алертом, а не строкой в логе на каждый запрос. |
| M-14 | `exception_handler(Exception)` с `raise exc` | `main.py` | Ре-raise внутри `ServerErrorMiddleware` обрывает соединение без тела ответа. На практике не срабатывает (HTTPException перехватывается раньше), но код мёртвый и вводит в заблуждение. |

### 4.2. Гигиена

- `utils.py` — дублирующиеся импорты (`PIL.Image`, `hashlib`, `magic` дважды),
  `except:` без типа в `validate_image_file`, мёртвые функции
  `validate_image_file` / `process_image` / `generate_thumbnail` /
  `compute_file_hash`.
- `crud.learn_products_from_feedback` — мёртвый код с предупреждением в
  докстринге. Лучше удалить.
- Нет ограничения длины пароля сверху и требований к сложности (только
  `min_length=8`).
- Нет верификации email при регистрации.
- `_build_profile` вызывает `get_latest_weight` дважды;
  `_build_workouts_payload` дважды вызывает `list_workouts`.
- `pydantic` v1-стиль (`@validator`, `@root_validator`) на pydantic 2.6 —
  работает через слой совместимости, при обновлении сломается.
- `gcc` остаётся в финальном образе (нет multi-stage для Python-части).
- Sentry не подключён — из наблюдаемости есть только Prometheus-метрики.

### 4.3. Обязательно перед 5000 DAU

**Нагрузочный тест.** Все расчёты в этом документе — оценки. Реальные цифры
даст только прогон с профилем нагрузки, повторяющим пики приёмов пищи
(19:00–21:00 может дать 30–40% дневного объёма).

Сценарий: логин → дневник → добавление еды → анализ фото. Инструмент —
locust. Смотреть: глубину очереди `analyze`, время ожидания коннекта из пула,
RSS контейнера celery, свободное место на томе uploads.
