# Функциональные требования — AI Healthy

Документ описывает функциональные требования к платформе AI Healthy — приложению для
учёта питания с автоматическим распознаванием КБЖУ (калории, белки, жиры, углеводы) по
фотографии блюда. Требования сгруппированы по функциональным модулям и предназначены для
проектирования автотестов.

Идентификатор требования: `FR-<МОДУЛЬ>-<номер>`.

---

## 1. Аутентификация и пользователи (AUTH)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-AUTH-01 | Пользователь может зарегистрироваться по email и паролю. Email уникален. | `POST /api/v1/register` |
| FR-AUTH-02 | При повторной регистрации существующего email возвращается ошибка `400` с текстом «Пользователь уже существует». | `POST /api/v1/register` |
| FR-AUTH-03 | Пароль при регистрации обязателен и должен содержать не менее 8 символов. | `POST /api/v1/register` |
| FR-AUTH-04 | При регистрации опционально принимаются `height_cm` и `weight_kg`. Если `weight_kg` задан, он становится первой записью истории взвешиваний с источником `registration`. | `POST /api/v1/register` |
| FR-AUTH-05 | Пользователь может войти по email и паролю и получить пару токенов (`access_token`, `refresh_token`). | `POST /api/v1/login` |
| FR-AUTH-06 | При неверных учётных данных возвращается `401` с текстом «Неверный email или пароль». | `POST /api/v1/login`, `POST /api/v1/token` |
| FR-AUTH-07 | Эндпоинт `/api/v1/token` поддерживает `grant_type=password` (логин) и `grant_type=refresh_token` (обновление токена). | `POST /api/v1/token` |
| FR-AUTH-08 | При `grant_type=refresh_token` без поля `refresh_token` возвращается `400`. При невалидном refresh-токене — `401`. | `POST /api/v1/token` |
| FR-AUTH-09 | Неподдерживаемый `grant_type` приводит к ошибке `400` «Unsupported grant_type». | `POST /api/v1/login`, `POST /api/v1/token` |
| FR-AUTH-10 | Авторизованный пользователь может получить данные своего профиля учётной записи. | `GET /api/v1/me` |
| FR-AUTH-11 | Все защищённые эндпоинты при отсутствии/невалидности `access_token` возвращают `401`. | все, кроме `/health`, `register`, `login`, `token` |
| FR-AUTH-12 | Авторизованный пользователь может сменить пароль, указав текущий и новый. Неверный текущий пароль → `400`; новый пароль, совпадающий с текущим → `400`. | `POST /api/v1/change-password` |
| FR-AUTH-13 | Смена пароля инкрементирует `token_version` пользователя — все токены, выданные до смены, немедленно перестают проходить проверку (`401`), даже если формально не истекли. Ответ содержит свежую пару токенов для текущей сессии. | `POST /api/v1/change-password` |

## 2. Профиль и история веса (PROFILE)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-PROF-01 | Пользователь может получить расширенный профиль: ФИО, рост, текущий вес, пол, дату рождения, уровень активности, последние записи веса и рассчитанные нормы (BMR, калории, БЖУ). | `GET /api/v1/profile` |
| FR-PROF-02 | Текущий вес (`current_weight_kg`) вычисляется как последняя запись истории взвешиваний, а не хранится отдельным полем. | `GET /api/v1/profile` |
| FR-PROF-03 | Пользователь может обновить поля профиля: `full_name`, `height_cm`, `weight_kg`, `sex`, `birth_date`, `activity_level`. Все поля опциональны (частичное обновление). | `PUT /api/v1/profile` |
| FR-PROF-04 | `sex` принимает только значения `male`/`female`; `activity_level` — только `sedentary`/`light`/`moderate`/`active`/`very_active`. Иные значения отклоняются с `422`. | `PUT /api/v1/profile` |
| FR-PROF-05 | При обновлении профиля вес попадает в историю (за сегодня) только если `save_weight_as_record=true` (по умолчанию) И значение отличается от последней записи. | `PUT /api/v1/profile` |
| FR-PROF-06 | Пользователь может добавить запись о взвешивании с указанием даты (`recorded_on`) и заметки (`note`). | `POST /api/v1/profile/weight` |
| FR-PROF-07 | Дата записи взвешивания не может быть в будущем — иначе `400` «Дата записи не может быть в будущем». | `POST /api/v1/profile/weight` |
| FR-PROF-08 | Повторное сохранение веса за тот же день обновляет существующую запись, а не создаёт дубликат (upsert по паре пользователь+дата). | `POST /api/v1/profile/weight`, `PUT /api/v1/profile` |
| FR-PROF-09 | Пользователь может получить историю взвешиваний с опциональной фильтрацией по диапазону дат (`start`, `end`). Записи отсортированы по дате по возрастанию. | `GET /api/v1/profile/weight-history` |
| FR-PROF-10 | Пользователь может отредактировать существующую запись взвешивания (вес, дату, обхваты, заметку) по её `id`. Перенос на дату, где уже есть запись, → `409`. | `PUT /api/v1/profile/weight/{record_id}` |
| FR-PROF-11 | Пользователь может удалить запись взвешивания по `id`. Чужая/несуществующая запись → `404`. | `DELETE /api/v1/profile/weight/{record_id}` |
| FR-PROF-12 | При регистрации и в записях взвешивания можно указать обхваты тела (талия/грудь/бёдра/плечи) — все опциональны, хранятся в той же строке истории, что и вес. | `POST /api/v1/register`, `POST /api/v1/profile/weight` |
| FR-PROF-13 | Пользователь может задать ручные нормы КБЖУ/воды (`custom_calorie_target`, `custom_protein_g`, `custom_protein_animal_g`, `custom_protein_plant_g`, `custom_fat_g`, `custom_carbs_g`, `custom_water_ml`), которые переопределяют автоматический расчёт везде (дневник, вода, советчик, тренировки). | `PUT /api/v1/profile` |

## 3. Анализ изображений (ANALYZE)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-ANL-01 | Авторизованный пользователь может загрузить фотографию блюда и поставить её в очередь на анализ. Создаётся задача со статусом `pending`, возвращается её `id`. | `POST /api/v1/analyze` |
| FR-ANL-02 | Загружаемый файл должен иметь одно из расширений: `.jpg`, `.jpeg`, `.png`, `.webp`. Иначе `400` «Unsupported file type». | `POST /api/v1/analyze` |
| FR-ANL-03 | Содержимое файла валидируется как изображение в формате JPEG/PNG/WEBP. Невалидное изображение → `400` «Uploaded file is not a valid image». | `POST /api/v1/analyze` |
| FR-ANL-04 | Размер файла не должен превышать 10 МБ. При превышении — `413` «Uploaded file is too large». | `POST /api/v1/analyze` |
| FR-ANL-05 | Анализ выполняется асинхронно (Celery). Статус задачи проходит цепочку `pending → processing → success`/`failure`. | `POST /api/v1/analyze`, `GET /api/v1/task/{task_id}` |
| FR-ANL-06 | Пользователь может узнать статус и результат задачи по её `id`. Результат включает название блюда, вес, КБЖУ, уверенность модели и состав (ингредиенты). | `GET /api/v1/task/{task_id}` |
| FR-ANL-07 | Доступ к задаче ограничен её владельцем. Запрос чужой/несуществующей задачи → `404` «Task not found». | `GET /api/v1/task/{task_id}` |
| FR-ANL-08 | Пользователь может получить историю своих задач с пагинацией (`limit`, `offset`), отсортированную по дате создания по убыванию. | `GET /api/v1/tasks` |
| FR-ANL-09 | Загруженные изображения доступны для предпросмотра по пути `/uploads/<filename>` (значение `image_path` в ответе задачи отдаётся как URL). | статика `/uploads` |

## 4. Дневник питания (DIARY)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-DIARY-01 | Пользователь может добавить запись о приёме пищи вручную: название, КБЖУ, вес, тип приёма (`meal_type`), дату. | `POST /api/v1/meals` |
| FR-DIARY-02 | `meal_type` принимает значения `breakfast`, `lunch`, `dinner`, `snacks` (по умолчанию `snacks`). | `POST /api/v1/meals` |
| FR-DIARY-03 | Запись приёма пищи можно создать из успешной задачи анализа: КБЖУ берутся из результата задачи. | `POST /api/v1/meals/from-analysis` |
| FR-DIARY-04 | Создание приёма из анализа доступно только для задачи в статусе `success` с непустым результатом. Иначе `400`. Чужая/несуществующая задача → `404`. | `POST /api/v1/meals/from-analysis` |
| FR-DIARY-05 | Пользователь может получить суточный дневник за указанную дату (`date_str`, формат `YYYY-MM-DD`; по умолчанию — сегодня). | `GET /api/v1/daily-log` |
| FR-DIARY-06 | Неверный формат даты в `date_str` → `400` «Invalid date format, expected YYYY-MM-DD». | `GET /api/v1/daily-log` |
| FR-DIARY-07 | Суточный дневник содержит суммарные КБЖУ за день, список приёмов пищи и суточные нормы (`targets`) пользователя. | `GET /api/v1/daily-log` |
| FR-DIARY-08 | За день без записей дневник возвращается с нулевыми суммами и пустым списком приёмов (не `404`). | `GET /api/v1/daily-log` |
| FR-DIARY-09 | Пользователь может отредактировать запись приёма пищи (все нутриенты, вес, название, тип). | `PATCH /api/v1/meals/{meal_id}` |
| FR-DIARY-10 | Пользователь может удалить запись приёма пищи. Возвращается `{status: ok, deleted_id}`. | `DELETE /api/v1/meals/{meal_id}` |
| FR-DIARY-11 | Редактирование/удаление чужой или несуществующей записи → `404` «Meal entry not found». | `PATCH/DELETE /api/v1/meals/{meal_id}` |
| FR-DIARY-12 | Запись приёма пищи может быть составной (несколько блюд в `items`); итоговые КБЖУ и вес записи — сумма по блюдам, пересчитываемая на бэкенде. | `POST/PATCH /api/v1/meals[...]` |
| FR-DIARY-13 | Пользователь может прикрепить или заменить фото записи приёма пищи; собственное фото приоритетнее фото, полученного из AI-анализа. | `POST /api/v1/meals/{meal_id}/photo` |
| FR-DIARY-14 | Пользователь может удалить своё фото записи; если запись создана из AI-анализа, `photo_url` возвращается к фото анализа. | `DELETE /api/v1/meals/{meal_id}/photo` |

## 5. Вода (WATER)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-WATER-01 | Пользователь может получить объём выпитой воды за дату (по умолчанию — сегодня) и суточную норму. | `GET /api/v1/water` |
| FR-WATER-02 | Пользователь может изменить объём: пустое тело `{}` добавляет один стакан (250 мл); `amount_ml` < 0 — убирает; итог не опускается ниже нуля. | `POST /api/v1/water` |
| FR-WATER-03 | Запись — одна на пару (пользователь, дата); повторные вызовы за один день суммируют/вычитают объём в существующей записи (upsert), а не создают дубли. | `POST /api/v1/water` |
| FR-WATER-04 | Дата не может быть в будущем — иначе `400`. | `POST /api/v1/water` |
| FR-WATER-05 | Норма воды (`goal_ml`) рассчитывается из веса и уровня активности пользователя; при отсутствии данных — `null` (см. бизнес-правила). Может быть переопределена вручную (`custom_water_ml`). | `GET /api/v1/water`, `GET /api/v1/profile` |

## 6. Продукты и штрих-коды (PRODUCTS)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-PROD-01 | Пользователь может искать продукт по названию в справочнике КБЖУ (`q`, `limit`) для автодополнения при ручном добавлении приёма пищи. | `GET /api/v1/products` |
| FR-PROD-02 | Пользователь может сфотографировать штрих-код упаковки; сервис декодирует код и ищет продукт в Open Food Facts, возвращая название и КБЖУ на 100 г. | `POST /api/v1/barcode/scan` |
| FR-PROD-03 | Пользователь может ввести штрих-код вручную и получить тот же результат, что и при сканировании. | `GET /api/v1/barcode/{code}` |
| FR-PROD-04 | Сканирование штрих-кода ограничено 100 запросами в сутки на пользователя. | `POST /api/v1/barcode/scan` |
| FR-PROD-05 | Фото штрих-кода не сохраняется на диске после обработки запроса (это не фото еды). | `POST /api/v1/barcode/scan` |

## 7. Тренировки (WORKOUT)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-WO-01 | Пользователь может добавить тренировку: тип (`strength`/`cardio`/`stretching`/`sport`/`other`), название, дату, длительность и потраченные калории (напрямую или через список упражнений `items`). | `POST /api/v1/workouts` |
| FR-WO-02 | При наличии `items` итоговые длительность и калории тренировки пересчитываются на бэкенде как сумма упражнений — значения с верхнего уровня запроса игнорируются. | `POST/PUT /api/v1/workouts` |
| FR-WO-03 | Пользователь может получить список тренировок за дату, сводку за день (сожжённые калории, длительность, количество) и суточную норму калорий, скорректированную на сожжённые. | `GET /api/v1/workouts` |
| FR-WO-04 | Ответ также содержит недельную полосу активности (Пн–Вс, содержащая выбранный день) с флагом «была тренировка» на каждый день. | `GET /api/v1/workouts` |
| FR-WO-05 | Пользователь может редактировать (полная замена упражнений) и удалять свои тренировки. Чужая/несуществующая тренировка → `404`. | `PUT/DELETE /api/v1/workouts/{workout_id}` |
| FR-WO-06 | Дата тренировки не может быть в будущем. | `POST/PUT /api/v1/workouts` |
| FR-WO-07 | Пользователь может искать упражнения в справочнике (`q`, `limit`) с расходом калорий (ккал/мин, ~70 кг) для авторасчёта в форме. | `GET /api/v1/exercises` |

## 8. AI-советчик (ADVISOR)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-ADV-01 | Пользователь может получить советы дня по питанию и тренировкам на основе текущего дневника, воды, тренировок и истории веса. | `GET /api/v1/advisor` |
| FR-ADV-02 | Советы формируются LLM (Yandex Cloud); при недоступности/ошибке LLM используется детерминированный фолбэк на правилах (без потери функциональности). | `GET /api/v1/advisor` |
| FR-ADV-03 | Ответ кэшируется в Redis по отпечатку контекста пользователя на 30 минут (LLM-ответ) или 2 минуты (фолбэк на правилах). | `GET /api/v1/advisor` |
| FR-ADV-04 | Пользователь может задать свободный вопрос советчику и получить текстовый ответ (до 2000 символов). | `POST /api/v1/advisor/ask` |
| FR-ADV-05 | Вопросы советчику ограничены 30 в сутки на пользователя. | `POST /api/v1/advisor/ask` |

## 9. Обратная связь и обучение (FEEDBACK)

| ID | Требование | Эндпоинт |
|----|-----------|----------|
| FR-FB-01 | Пользователь может отправить исправление результата анализа: корректное название блюда (`correct_food`) и вес (`correct_weight`). | `POST /api/v1/feedback` |
| FR-FB-02 | Фидбек привязывается к задаче пользователя; чужая/несуществующая задача → `404`. | `POST /api/v1/feedback` |
| FR-FB-03 | `correct_food` — строка 1..200 символов; `correct_weight` — целое > 0 и ≤ 10000. Нарушение → `422`. | `POST /api/v1/feedback` |
| FR-FB-04 | Накопление фидбеков используется для дообучения справочника продуктов; при достижении 10 необработанных фидбеков запускается переобучение модели. | внутренняя логика |
