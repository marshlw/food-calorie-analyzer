# Бизнес-правила — AI Healthy

Документ фиксирует расчётную и поведенческую логику системы. Это ключевой источник для
написания проверочных (assertion) автотестов: здесь приведены точные формулы, коэффициенты
и пограничные условия.

Идентификатор правила: `BR-<номер>`.

---

## 1. Расчёт BMR (базовый обмен веществ)

**BR-01.** BMR рассчитывается по формуле **Миффлина — Сан-Жеора**:

```
BMR = 10 × вес(кг) + 6.25 × рост(см) − 5 × возраст(лет) + S
где S = +5 для мужчин (male), −161 для женщин (female)
```

- Результат округляется до 1 знака после запятой.
- **BR-01.1.** Если хотя бы одно из значений (вес, рост, возраст, пол) отсутствует — BMR = `null` (и все производные нормы тоже `null`).
- **BR-01.2.** Вес для расчёта берётся из последней записи истории взвешиваний, рост и пол — из профиля пользователя.

**Пример:** мужчина, 80 кг, 180 см, 30 лет →
`10×80 + 6.25×180 − 5×30 + 5 = 800 + 1125 − 150 + 5 = 1780.0` ккал.

---

## 2. Возраст

**BR-02.** Возраст — число полных лет на текущую дату:

```
age = today.year − birth_date.year − (1, если (today.month, today.day) < (birth_date.month, birth_date.day))
```

- При отсутствии `birth_date` возраст = `null`.

---

## 3. Норма поддержания веса (TDEE)

**BR-03.** Норма поддержания = `BMR × коэффициент активности`, округление до целого.
Это база: цель пользователя даёт отклонение именно от неё (см. BR-03A).

Коэффициенты активности:

| activity_level | коэффициент |
|----------------|-------------|
| `sedentary` | 1.2 |
| `light` | 1.375 |
| `moderate` | 1.55 |
| `active` | 1.725 |
| `very_active` | 1.9 |

- **BR-03.1.** Если `activity_level` не задан или неизвестен — применяется коэффициент `1.2` (sedentary).
- **BR-03.2.** Если BMR = `null`, норма калорий = `null`.

**Пример:** BMR 1780, `moderate` → `round(1780 × 1.55) = 2759` ккал.

---

## 3A. Цель по весу → суточная норма калорий

**BR-03A.** Профиль хранит цель (`goal` ∈ `lose` | `maintain` | `gain`), желаемый темп
(`goal_rate_kg_per_week`, кг/нед) и опциональный целевой вес (`target_weight_kg`).
`goal = null` трактуется как `maintain` — существующие пользователи получают прежнюю норму.

Суточная поправка калорий считается **из темпа**, а не фиксированным процентом:

```
delta = ± rate_kg_per_week × KCAL_PER_KG / 7
```

| Направление | KCAL_PER_KG | Обоснование |
|-------------|-------------|-------------|
| `lose` | 7700 | энергия 1 кг жировой ткани |
| `gain` | 6000 | 1 кг смешанной ткани (мышцы + жир) дешевле |

Темп по умолчанию: `lose` — 0.5, `gain` — 0.25, `maintain` — 0 кг/нед.

**BR-03A.1. Ограничители безопасности** применяются по порядку; каждое срабатывание
возвращается клиенту в `calc_warnings` (`{code, message}`):

| # | Код | Правило |
|---|-----|---------|
| 1 | `rate_capped` | темп ≤ 1% массы тела в неделю при похудении и ≤ 0.5% при наборе |
| 2 | `deficit_capped` / `surplus_capped` | дефицит ≤ 25% TDEE, профицит ≤ 20% TDEE |
| 3 | `below_bmr` | итоговая норма не ниже BMR |
| 4 | `absolute_floor` | не ниже 1500 ккал (мужчины) / 1200 ккал (женщины) |

**BR-03A.2.** Прогноз сроков строится **от фактического темпа после ограничителей**,
а не от запрошенного: `weeks_to_goal = remaining_kg / applied_rate_kg_per_week`.
Без `target_weight_kg` прогноза нет.

**BR-03A.3.** Если до целевого веса осталось < 0.5 кг — цель считается достигнутой
(`goal_reached`), норма рассчитывается как поддержание. Если целевой вес противоречит
цели (похудение при целевом весе выше текущего) — `target_conflicts_goal`, прогноз
не строится, норма под цель выдаётся.

**BR-03A.4.** При смене цели ранее заданный темп сбрасывается на дефолтный: 0.5 кг/нед
безопасны для похудения, но вдвое превышают безопасный темп набора.

**Пример:** TDEE 2759, цель `lose`, темп 0.5 кг/нед → `delta = −550` → норма `2209` ккал.

---

## 4. Нормы макронутриентов (БЖУ)

**BR-04.** БЖУ считаются **снизу вверх** от массы тела, а не долями от калорий: доли
при 1300 ккал дают ~97 г белка, а при 3500 ккал — ~260 г, тогда как потребность в
белке зависит от массы тела, а не от калорийности.

Порядок: белок → жир → углеводы остатком.

| Макронутриент | Правило | ккал на 1 г |
|---------------|---------|-------------|
| Белки | г/кг референсной массы: `lose` 1.8, `maintain` 1.4, `gain` 1.8 + надбавка за активность (−0.2…+0.3), коридор 1.2–2.4 | 4.0 |
| Жиры | г/кг: `lose` 0.9, `maintain`/`gain` 1.0; не ниже 0.8 г/кг и коридор 20–40% калорий | 9.0 |
| Углеводы | остаток калорий, не менее 100 г | 4.0 |

**BR-04.1. Референсная масса.** При ИМТ ≤ 30 это фактический вес. Выше — скорректированная
масса `W25 + 0.25 × (факт − W25)`, где `W25` — вес при ИМТ 25: жировая ткань метаболически
малоактивна, и г/кг от фактических 140 кг дал бы нереалистичные ~266 г белка.

**BR-04.2.** Если остатка на углеводы не хватает (низкая калорийность при большой массе),
сначала жир ужимается до 0.8 г/кг, затем белок — но не ниже 1.2 г/кг.

**BR-04.3.** Если вес неизвестен, используется резервное распределение 25/30/45 от калорий.

**BR-04.4.** Если норма калорий = `null`, все нормы БЖУ = `null`.

**Пример:** мужчина 80 кг / 180 см, `moderate`, цель `lose` 0.5 кг/нед → 2209 ккал:
белки `80 × 1.9 = 152` г, жиры `80 × 0.9 = 72` г, углеводы `(2209 − 608 − 648)/4 = 238` г.

## 5. История взвешиваний

**BR-05.** Текущий вес пользователя = последняя запись истории (сортировка по `recorded_on` убыв., затем по `created_at` убыв.). Отдельного поля «текущий вес» в БД нет.

**BR-06.** Одна запись на пару (`user_id`, `recorded_on`). Повторное сохранение веса за тот же день **обновляет** существующую запись (upsert), а не создаёт новую.

**BR-07.** Дата записи взвешивания (`recorded_on`) **не может быть в будущем** → `400`.

**BR-08.** Источник записи (`source`):
- `registration` — вес, указанный при регистрации;
- `profile_edit` — вес из формы редактирования профиля;
- `manual` — добавлен вручную через `POST /profile/weight`.

**BR-09.** Вес из формы профиля попадает в историю **только если** `save_weight_as_record=true` (по умолчанию) **и** новое значение отличается от последней записи.

---

## 6. Жизненный цикл задачи анализа

**BR-10.** Статусы задачи и переходы:

```
pending ──(воркер взял в работу)──► processing ──(успех)──► success
   │                                     │
   └──(сбой постановки в очередь)        └──(ошибка модели)──► failure
        ──► failure
```

**BR-11.** При сбое постановки задачи в очередь Celery: статус → `failure`, поле `error` заполняется, загруженный файл удаляется, клиенту возвращается `500`.

**BR-12.** Результат анализа (`NutritionResponse`) доступен только в статусе `success` и непустом `result_json`.

**BR-13.** Идентичные изображения (по хэшу) обслуживаются из Redis-кэша (TTL 24 ч) без повторного вызова ML-модели.

---

## 7. Изоляция данных (владение ресурсами)

**BR-14.** Пользователь имеет доступ только к своим задачам, записям дневника, фидбекам и истории веса. Обращение к чужому ресурсу неотличимо от несуществующего — возвращается `404` (а не `403`), чтобы не раскрывать факт существования объекта.

---

## 8. Создание приёма пищи из анализа

**BR-15.** `POST /meals/from-analysis` допустимо только если:
1. задача существует и принадлежит пользователю (иначе `404`);
2. статус задачи = `success` (иначе `400` «Analysis task is not successful»);
3. `result_json` не пуст (иначе `400` «Analysis result is missing»).

**BR-16.** КБЖУ приёма берутся из результата задачи; название блюда — из `food`/`food_name`, при отсутствии — `"analyzed meal"`. Отсутствующие нутриенты подставляются как `0`.

---

## 9. Суточный дневник

**BR-17.** Суммарные КБЖУ дня = сумма соответствующих полей всех `MealEntry` за день, округление до 1 знака.

**BR-18.** За день без записей возвращается дневник с нулевыми суммами, пустым списком `meals` и заполненными `targets` (нормы не зависят от наличия записей).

**BR-19.** Нормы КБЖУ (`targets`) в дневнике одинаковы для любой даты — это текущие суточные нормы пользователя (см. BR-03, BR-04).

---

## 10. Обратная связь и дообучение

**BR-20.** Каждый фидбек дообучает справочник продуктов: новые ингредиенты из предсказания (имя ≥ 3 символов, ещё не существующие) добавляются в `products` с базовой оценкой КБЖУ.

**BR-21.** При накоплении **≥ 10** фидбеков в статусе `pending` автоматически запускается задача переобучения модели (`retrain_model_task`).

---

## 11. Валидация загрузки изображения

**BR-22.** Файл принимается, если выполняются ВСЕ условия:
1. расширение ∈ {`.jpg`, `.jpeg`, `.png`, `.webp`} (иначе `400` «Unsupported file type»);
2. размер ≤ 10 МБ (иначе `413` «Uploaded file is too large»);
3. содержимое — валидное изображение формата JPEG/PNG/WEBP (иначе `400` «Uploaded file is not a valid image»).

**BR-23.** При обработке изображение конвертируется в RGB, у него удаляется EXIF, выполняется ресайз (до 1600 px по большей стороне). Имя файла на диске — случайный UUID.

---

## 12. Аутентификация и токены

**BR-24.** Access-токен живёт 30 минут, refresh — 7 дней. Тип токена (`access`/`refresh`) проверяется при декодировании; использование refresh-токена там, где ожидается access (и наоборот) → `401`.

**BR-25.** Пароль усекается до 72 байт перед хэшированием bcrypt (ограничение алгоритма) — пароли, различающиеся только после 72-го байта, считаются одинаковыми.

**BR-26.** Обновление токенов: `grant_type=refresh_token` с валидным `refresh_token` возвращает новую пару `access`+`refresh`.
